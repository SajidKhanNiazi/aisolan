## 1. Overview & Architecture

BookPilot AI Phase 1G-A implements a **durable transactional outbox pattern** for all appointment email notifications:

```
[Appointment Event (Commit)] ──► [PostgreSQL Outbox Table] ──► [Atomic Worker (FOR UPDATE SKIP LOCKED)] ──► [Resend API] ──► [Delivery Audit]
```

- **Zero Lost Bookings:** Email provider delays, rate limits, or transient outages never fail or roll back an appointment transaction.
- **Trigger Fault Tolerance:** Nonessential email preparation errors inside the trigger are gracefully caught and suppressed with database warnings (`EXCEPTION WHEN OTHERS`), ensuring that valid appointment transactions are never aborted by notification logic.
- **Zero-Race Atomic Management URL:** Public bookings pass `p_management_url` directly to `create_public_appointment_atomic`, enriching the outbox record inside the exact same database transaction. A background worker can never claim an unpopulated or tokenless confirmation email.
- **Column-Level Privacy Enforcement:** PostgreSQL engine permissions strictly revoke `SELECT (payload)` from tenant users (`authenticated`). The salon owner dashboard history query omits `payload`, guaranteeing that customer self-service management links are never visible to salon owners or leaked into client-side state.
- **Provider-Side Idempotency:** The Resend provider passes `idempotencyKey` via the official SDK request options (`Idempotency-Key` HTTP header), eliminating duplicate emails in retry and network timeout scenarios.
- **Fail-Safe Gate:** If `RESEND_API_KEY` is omitted, the system operates in **Mock Delivery Mode** without breaking or throwing runtime errors.

## 2. Step-by-Step Resend Account & Domain Setup

### Step 2.1: Create Resend Account & Add Domain
1. Log in to [resend.com](https://resend.com).
2. Navigate to **Domains** &rarr; **Add Domain**.
3. Enter your verified production sending domain (e.g. `mail.aisolan.com` or `aisolan.app`).
4. Select your primary region (e.g. EU/Frankfurt or US/North Virginia).

### Step 2.2: Configure DNS Records
Add the DNS records generated by Resend to your DNS provider (e.g. Cloudflare, Namecheap, Vercel DNS):

| Type | Name | Content / Value | Purpose |
| :--- | :--- | :--- | :--- |
| **TXT** | `resend._domainkey` | `k=rsa; p=...` (Provided by Resend) | DKIM cryptographic authentication |
| **TXT** | `@` or sub-domain | `v=spf1 include:amazonses.com ~all` | SPF email sender authorization |
| **MX** | `feedback` | `feedback-smtp.resend.com` (Priority 10) | Inbound bounce & complaint handling |
| **TXT** | `_dmarc` | `v=DMARC1; p=none; rua=mailto:...` | DMARC compliance policy |

Wait for Resend to verify all DNS records (status: **Verified**).

### Step 2.3: Generate a Restricted Production API Key
1. Go to **API Keys** &rarr; **Create API Key**.
2. **Name:** `BookPilot AI Production Worker`.
3. **Permission:** **Sending access** (Restricted to your verified sending domain).
4. Copy the key (`re_...`) securely to your password manager.

## 4. Vercel Cron, Next.js `after()`, & Hostinger Alternative

### 4.1 Immediate Delivery via Next.js `after()` (Best-Effort Fast Path)
Customer booking confirmations, cancellations, and reschedules trigger immediate, non-blocking background queue processing via Next.js `after()`. Under normal execution, emails are dispatched within **1–2 seconds** after transaction commit.

> [!NOTE]
> Next.js `after()` is an opportunistic, best-effort latency optimization. If a serverless function experiences a timeout, cold abort, or immediate lifecycle termination, asynchronous promises in `after()` can be canceled. Therefore, the PostgreSQL `notification_outbox` table remains the durable source of truth, and a periodic polling sweeper is required to reliably process retries and missed jobs.

### 4.2 Vercel Plan Limits & Built-in Sweeper
Vercel enforces strict limits on cron frequency based on your plan:

- **Hobby Plan (Free):** Only allows cron jobs to run **at most once per day** (`0 8 * * *`). Sub-daily schedules (`* * * * *` or `*/5 * * * *`) cause Vercel deployment to **fail**.
- **Pro Plan ($20/mo):** Allows sub-daily schedules up to **once per minute** (`* * * * *`).

The project provides a plan-safe `vercel.json` configured for daily sweeper execution:
```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "crons": [
    {
      "path": "/api/internal/notifications/process",
      "schedule": "0 8 * * *"
    }
  ]
}
```

### 4.3 Secure Hostinger Business Cron Alternative (Sub-Daily Polling on Hobby)
If the Vercel project remains on the Hobby plan but frequent queue polling (e.g., every 1 or 5 minutes) is desired, you can use **Hostinger Business Web Hosting Cron Jobs** to poll the worker securely via HTTPS without paying for Vercel Pro.

**Security Constraints:**
- Authentication secret must **NEVER** be placed in query parameters (which can be exposed in browser history, CDN logs, or access logs).
- Secret must be sent exclusively in the HTTP `Authorization` or `x-cron-secret` header over TLS (`https://`).
- Command execution output must be discarded (`-o /dev/null`) so tokens and payloads are not written to shared system logs.

**Configuration in Hostinger hPanel &rarr; Advanced &rarr; Cron Jobs:**
1. **Type:** Custom
2. **Frequency:** `*/5 * * * *` (every 5 minutes) or `* * * * *` (every minute)
3. **Command:**
```bash
curl -s -S -X POST "https://aisolan.vercel.app/api/internal/notifications/process" \
  -H "Authorization: Bearer YOUR_CRON_SECRET_HERE" \
  -H "Content-Type: application/json" \
  -o /dev/null
```

> [!IMPORTANT]
> Hostinger cron configuration is optional and must **NOT** be enabled without explicit owner approval. Vercel Hobby daily cron + Next.js `after()` is already functional out of the box.

## 5. Testing Email Delivery Safely

### 5.1 Local Verification (Mock Mode)
In local development, leave `RESEND_API_KEY` blank. The worker dispatches to `MockDeliveryProvider`, logs message summaries safely without leaking customer credentials, and marks rows as `sent`.

### 5.2 Staging / Sandbox Verification
1. Set `RESEND_API_KEY` to your test key.
2. In Resend sandbox mode, emails can be sent to `delivered@resend.dev` (simulates successful delivery) or `bounced@resend.dev` (simulates permanent bounce).
3. Trigger a test booking on `/booking/<salon-slug>`.
4. Trigger worker via curl:
```bash
curl -X GET "https://aisolan.vercel.app/api/internal/notifications/process" \
     -H "Authorization: Bearer <YOUR_CRON_SECRET>"
```
5. Check response:
```json
{
  "success": true,
  "processed": 2,
  "succeeded": 2,
  "retried": 0,
  "failed": 0
}
```

### 6.4 Outbox Reconciliation, Anti-Staleness & Bounded Idempotency

#### A. Canonical Missing Notification Detection & Safe Recovery
In the canonical database schema, appointments do not store customer email directly; email is stored on `public.customers (business_id, id)` and referenced via `appointments.customer_id`.

To safely detect confirmed appointments that missed outbox enqueuing without sending obsolete emails or duplicates:
```sql
-- 1. Identify missing confirmed notifications
SELECT 
    a.id AS appointment_id,
    a.business_id,
    c.id AS customer_id,
    c.email AS customer_email,
    c.name AS customer_name,
    a.starts_at,
    a.status
FROM public.appointments a
JOIN public.customers c 
    ON c.business_id = a.business_id 
   AND c.id = a.customer_id
LEFT JOIN public.notification_outbox n 
    ON n.appointment_id = a.id 
   AND n.template_key = 'customer_booking_confirmation'
WHERE a.created_at >= NOW() - INTERVAL '7 days'
  AND a.status = 'confirmed'
  AND c.email IS NOT NULL
  AND c.email ~* '^.+@.+\..+$'
  AND n.id IS NULL;
```

#### B. Anti-Staleness: Preventing Obsolete Emails After Cancellation
BookPilot AI enforces a two-layer defense against sending stale booking/reschedule confirmations after an appointment is cancelled:
1. **Database Trigger:** When an appointment status transitions to `'cancelled'`, the trigger immediately updates all existing outbox records in `'queued'` or `'retry_pending'` status for that appointment to `'skipped'` with message `'Superseded by appointment cancellation'`.
2. **Worker Pre-Flight Check:** Before dispatching any `new_booking` or `reschedule` email, the queue worker inspects `appointments.status`. If the appointment was cancelled in the interim, the job is marked `'skipped'` (`APPOINTMENT_CANCELLED`) and never sent.

#### C. Bounded Provider Idempotency
- Provider deduplication via `idempotencyKey` (`dedupe_key`) is **bounded** to Resend's 24-hour cache window. It is not an infinite guarantee of exactly-once email delivery across multi-day network failures.
- The queue worker's exponential backoff (`min(3600, 2^(attempt - 1) * 30)`) and maximum attempt limit (`max_attempts = 5`) ensure that all automatic retries terminate within ~15 minutes—well within the provider's active 24-hour deduplication window.
